# Linear 敏捷开发使用指南（How-to）

> 适用范围：Lovart 移动端
> 工具：Linear
> 目的：统一工作方式，减少沟通成本

---

## 我们的敏捷原则 (Agile Principles)

在 Lovart 移动端：
* **Agile = 持续、小步地交付可工作的结果**
* **优先发布，越快越好**
* **不追求完美**
* **绝不假设所有产品改动总是能带来正面结果**
* **快速试错并调整方向**
* **测量一切，使用数据驱动的方法指导产品决策**
* **流程可见性：工作流程和进度应对所有人可见，无论其角色或职级**
所有工作通过 
**Issue / Project / Status / Label** 进行表达。

---

## 定义

### Issue
* Issue 是一个独立的工作单元，可以由单个人完成
* **所有开发工作必须有 Issue**
* **Issue 描述**：
  * 我们不强制要求每个人填写 Issue 描述
  * 但强烈建议使用 AI 来撰写 Issue 描述
  * AI 可以帮助生成清晰、完整的任务说明，提高团队协作效率
* 在敏捷开发中，我们希望 Active 看板保持持续流动
* 因此，最好将较大的 Issue 拆分为多个可以按顺序执行的小 Issue
* **Issue 时长指导**：
  * 单个 Issue 从开始到完成不应超过 3 个工作日
  * 如果预计超过此时长，应拆分为多个小 Issue
* **每周期 Issue 数量期望**：
  * 2 周周期：每个开发者完成 4-6 个 Issue
  * 1 周周期：每个开发者完成 2-3 个 Issue
  * 实际数量会根据 Issue 复杂度、依赖关系和突发情况调整
  * 这些指导原则将在 Retro 会议中根据实际情况进行调整
* **Issue 优先级**：
  * 所有处于 Active 状态的 Issue 必须设置优先级
  * 优先级级别：
    * **Urgent（紧急）**：必须在当前周期发布前完成
    * **High（高）**：可以在当前周期完成，但不是必须的
    * **Medium（中）**：应该移到下一个周期
    * **Low（低）**：应记录但忽略，移入 "Won't work"
  * 优先级确定方式：
    * **Feature、Data、Improvement**：由开发Leader在 Cycle Planning 期间确定
    * **Bug**：由 QA 和开发Leader在问题分级（Triage）会议期间确定

### Issue 状态

> 状态表达的是**当前事实**，不是期望

* **Backlog**
  * 新创建的 Issue
  * 尚未决定何时做
  * 在Cycle planning会议中，将Issue分配给开发成员并挪入 Todo

* **Todo**
  * 本Cycle决定要做的事项，但尚未开始
  * 进入 Gathering：准备开始收集实现所需信息时

* **Gathering**
  * 阅读产品需求文档和Figma设计稿
  * 查找第三方 SDK 相关文档（如需要）
  * 向设计师澄清模糊的交互行为
  * 与数据分析师讨论需要添加的分析事件
  * 收集其他实现所需的技术或业务信息
  * 目标：将开放的 Issue 转化为定义明确、可交给 AI 实现的 Issue
  * 进入 Planning：所有上下文信息收集完成，可以开始编写计划文档时

* **Planning**

  * 编写或完善计划文档（Plan Doc）
  * 计划文档应遵循计划模板（`templates/plan-template.md`）的结构
  * **计划文档审查**（推荐）：
    * 在 Cursor、Claude Code 或 Codex 中完成计划文档初稿后
    * 建议使用 ChatGPT 或 Claude 的扩展思考（Extended Thinking）功能来审查计划文档
    * 向 AI 提问：文档中哪些部分写得好？哪些部分不够好？还缺少什么内容？
    * 根据 AI 的反馈完善计划文档
  * 目标：完成计划文档，确保计划完成度超过 95% 后进入 Vibing 开始开发
  * 进入 Vibing：计划文档完成，计划完成度超过 95% 时

* **Vibing**
  * 执行计划文档中的实施步骤
  * 完成单个或多个步骤后提交代码（commit and push）
  * 确保 iOS 和 Android 应用仍能正常编译
  * 确保所有单元测试通过
  * 测试功能是否正常工作
  * 如果功能不工作，使用 AI 帮助debug
  * 进入 Testing：所有实施步骤完成，功能基本实现时
  
* **Testing**
  * 为服务层变更添加新的单元测试
  * 执行计划文档中定义的手动测试
  * 确保功能按预期工作后合并代码，进入Done
  * 进入 Done：所有测试通过，代码已合并时
  
* **Done**
  * 代码已合并

* **Blocked**
  * 等待外部依赖，例如：
    * 后端服务尚未可用
    * 等待决定使用哪个第三方服务
    * 功能与其他正在进行的实验冲突，需要延迟发布
    * 其他人员正在重构/重做该功能依赖的组件

* **Won't work**
  * **重要说明**：Won't work 不等于问题不重要，而是当前资源和时机下的显性决策
  * 已知风险或已知 Bug，但影响较小，修复所需工作量过大
  * 团队有意决定暂不处理
  * 将在团队和公司有更多资源时再处理
  * 可能通过重构整个组件或整个应用来解决

* **Canceled**
  * 明确决定不再处理（延迟的 Issue 应移回 Backlog）
  * 计划变更导致取消，例如：
    * Bug 无法可靠复现，无法确定原因
    * 功能已被更新更好的方案取代

### Project（用于追踪阶段性目标）
* Project 可以跨越单个周期（Cycle）或多个周期
* 一个 Project 可以同时有多个开发者参与
* Project 的 Assignee 是该项目的开发Leader（Lead Developer）
* 开发Leader负责：
  * 将 Project 拆分为多个 Issue
  * 将 Issue 分配给支持开发者完成
  * 解除阻塞（unblock Issue），确保项目持续进展，避免停滞
  * 在 Linear 上更新 Project 的状态
  * 每个 Cycle 结束后，在 Project 上用 comment 的形式说明：
    * 本 Cycle 完成了什么
    * 发布前还需要完成什么
* **团队规模和项目数量管理**：
  * 团队规模应在 3-7 人之间
  * **团队不应有比人数更多的进行中的项目**（ongoing projects）
  * 如果计划的项目数量超过现有人员能够支持的数量，应：
    * 考虑招聘更多开发者
    * 或将移动团队拆分为可以独立运作的小单元（smaller units）

### Project 状态

> 适用范围：Lovart
> 说明：Project 层级状态为 **统一约定含义**，不可按个人或团队自行解释

#### Backlog

**产品需求文档已完成**

* PRD / 产品需求说明已准备完成
* 功能范围、目标已明确
* 尚未进入开发阶段

---

#### Planned

**功能正在开发中**

* 工程实现已开始
* 功能尚未对用户开放
* 不涉及实验或线上验证

---

#### In Progress

**实验（A/B Test）进行中**

* 功能已对部分用户开放
* 实验正在收集数据
* 此阶段不得进行 100% 发布或代码清理
* **注意**：如果项目不涉及 A/B 测试，应跳过此状态

---

#### Completed

**实验结果为正，已全量发布并完成清理**

* A/B 实验结果为正
* 功能已 rollout 至 100% 用户
* 实验代码、feature flag、临时逻辑已全部清理完成

---

#### Canceled

**实验结果为负，已回滚并完成清理**

* A/B 实验结果为负
* 功能已 rollback 至 0% 用户
* 实验代码、feature flag、临时逻辑已全部清理完成

### 里程碑（Milestone）

* **定义**：里程碑是一个基于截止日期的容器，用于将跨项目、跨团队和跨工作流程的相关 Issue 进行分组，用于回答："我们是否能在日期 Y 之前交付 X？"
* **用途**：跟踪大型计划或跨团队协作的进度，确保按时交付
* **设置要求**：
  * 对于有目标日期的 Project，其开发Leader应设置里程碑来跟踪进度
  * 里程碑应包含所有与交付目标相关的 Issue，无论这些 Issue 属于哪个 Project 或团队

### 目标日期（Target Date）

* **定义**：目标日期是 Project 的预期完成日期
* **使用场景**：
  * **并非所有 Project 都需要目标日期**
  * 目标日期主要用于对齐大型计划（Bigger Initiatives）
  * **示例**：在 2026 年 3 月 1 日同时在所有平台推出协作功能
* **设置原则**：
  * 仅对需要跨团队协调、有明确交付时间要求的大型计划设置目标日期
  * 日常开发工作或探索性项目通常不需要设置目标日期

### 周期 （Cycle）
* 开发周期等同于发布周期（Release Cycle）
* 初始阶段：发布周期为 2 周
* 随着团队成员熟悉方法论后：每个周期为 1 周

#### 第 1 周

| | 星期一 | 星期二 | 星期三 | 星期四 | 星期五 |
|---|---|---|---|---|---|
| | Cycle 计划 | Standup | Standup | Standup | Standup |
| | | | | | 封版 (Release Cut) (11:00) |
| | | | | | 回归测试（第一天） |

#### 第 2 周

| | 星期一 | 星期二 | 星期三 | 星期四 | 星期五 |
|---|---|---|---|---|---|
| | Standup | 问题分级 （Triage） | Standup | Standup | Retro |
| | 回归测试（第二天） | 缺陷修复（第一天） | 缺陷修复（第二天） | Go/No-Go (17:00) | |
| | | | | 发布 | |

### 周期计划（Cycle Planning）会议

* 参会人员：所有开发团队成员、产品经理（PM）、设计师
* Cycle 计划 是每个开发者决定下一个 Cycle 要做什么工作的会议
* 时间： retro后的周一
* 会议内容：
  * 开发Leader将 Project 拆分为多个 Issue，并分配给其他开发者
  * 开发Leader为每个 Issue 分配优先级
  * 部分 Bug 将决定移入 "Won't work"
  * 其余 Bug 将在发布前修复

### Standup 会议

* 参会人员：所有开发团队成员
* Standup 是每个开发团队成员分享以下信息的会议：
  * 正在做什么工作
  * 当前工作状态
  * 是否有阻塞（blockers）
  * 接下来计划做什么
* 在有周期计划（Cycle Planning）、Retro 或问题分级（Triage）会议的日子，不进行 Standup

### 问题分级（Triage）会议

* 参会人员：QA、所有开发团队成员
* 问题分级会议用于决定 Bug 的优先级：
  * **Urgent**：必须在发布前通过热修复修复
  * **High**：可以在当前周期完成，但不是必须的
  * **Medium**：应该移到下一个周期
  * **Low**：移入 "Won't work"

### Go/No-Go 会议

* 参会人员：QA、所有开发团队成员
* Go/No-Go 是 QA 和所有开发者之间的会议
* 如果确认所有回归 Bug Issue 已在发布候选版本中修复，则 Go（发布）
* 否则 No-Go（跳过本次发布）

### Retro 会议

* 参会人员：所有开发团队成员
* Retro 会议用于讨论上一个 Cycle 中哪些做得好，哪些做得不好
* 也是提出对当前工作流程改进建议的时机
* 例如：可以建议修改计划模板、PR 模板等，或建议将周期缩短为 1 周，或建议调整standup的频率
* 没有什么是不可改变的
* 开发团队要在变化中寻找最适合当前人员配置、工作强度和工作复杂度的方式，持续优化工作流程
* 开发团队成员在 Retro 中提出的每个问题都会由工程负责人（Eng Lead）评估并决定如何改进
* **工作流程变更规则**：
  * 工作流程的变更将在 Retro 会议中讨论并决定
  * 在周期（Cycle）进行期间，不得以任何形式更改工作流程
  * 规则变更不能与我们的敏捷原则相违背
* **Retro 会议后**：
  * 每个开发Leader（Lead Developer）应在 Linear 上为其负责的 Project 撰写项目更新（Project Update）
  * 项目更新应说明本周期完成的工作、当前进度和下一步计划

### A/B 测试 (A/B Testing)

A/B 测试是一种数据驱动的功能验证方法，用于评估新功能对产品指标的影响。

#### 基本原理

* **测试形式**：对比开启功能的产品版本（B 组）与关闭功能的产品版本（A 组）
* **不预设结果**：我们绝不假设新功能必然带来正面结果，因此需要：
  * 明确定义要测量的指标
  * 设定预期目标
  * 通过实际数据验证假设
* **统计显著性**：只有当获得统计显著的结果时，才决定：
  * 将功能全量发布（100% rollout）
  * 或完全移除功能

#### 风险控制

* **风险暴露范围**：任何新功能在规模化场景下都未经充分验证，可能产生设计阶段未预见的负面影响
* **用户分组策略**：
  * 5% 用户：A 组（功能关闭）
  * 5% 用户：B 组（功能开启）
  * 90% 用户：默认关闭
* **风险最小化**：通过限制功能暴露范围至 5% 用户群体，将潜在风险影响控制在最小范围内

### 分阶段发布 (Phase Rollout)

分阶段发布是一种渐进式功能发布策略，适用于已确定需要全量发布的功能，但仍需控制风险暴露的场景。

#### 适用场景

* 品牌重塑（Rebrand）
* 重大设计改版（Major Redesign）
* 重大架构变更（Major Architecture Change）
* 其他已确定需要全量发布但风险较高的功能

#### 发布流程

* **初始阶段**：从 2% 用户开始发布
* **持续监控**：
  * 监控核心业务指标（Analytics）
  * 监控错误报告数据（Error Reporting）
  * 监控崩溃率（Crash Rate）
* **异常处理**：
  * 如发现核心指标大幅下降、错误率或崩溃率激增
  * 必须立即回滚至 0%
  * 使用数据调查根本原因
  * 重新评估并应用修复方案
  * 修复完成后重新开始分阶段发布

#### 时间成本

* **发布周期**：分阶段发布通常需要数周至一个月的时间
* **对开发流程的影响**：会减缓功能发布速度
* **使用建议**：
  * **早期阶段**：在产品方向频繁调整的早期阶段，不必对所有功能都执行分阶段发布
  * **成熟阶段**：只有当产品已证明成功且稳定后，才需要严格执行分阶段发布流程

### 封板 (Release cut)
* 封板是从 master/main 分支创建发布分支的时间点
* 流程：
  * 从 master/main 创建发布分支
  * 构建发布候选版本
  * 将发布候选版本发送给 QA
  * 时间：第一周周五上午 11:00 am

### 发布分支(Release branch)命名规则：`release-1-*-*`
  * 第一个版本号：始终为 1（除非有重大更新）
  * 第二个版本号：每个 Cycle 递增
  * 第三个版本号：封板时为 0；当发现 Bug 并修复时，创建热修复分支并递增此数字；

### 发布/回归测试
* 封板(Release cut)后，QA 对发布候选版本进行发布/回归测试)
* 测试在 PRE 环境进行，所有功能标志（feature flags）已禁用
* 发布测试不会测试新功能

### 热修复（Hot Fix）
* 当发布测试中发现 Bug 并修复时的流程：
  * 先将修复合并到 master/main
  * 基于上一个发布分支（release branch）创建新的热修复分支（hot fix branch）, 递增发布分支的第三个版本号
  * 将修复通过 cherry-pick 到新创建的热修复分支
  * 构建新的发布候选版本
* 绝大多数 Bug 修复应由开发者修复并验证
* 只有 Urgent 且难以复现的 Bug Issue 需要在基于新创建发布分支构建的新发布候选版本上再次进行 QA 测试
* 持续创建新的发布分支和发布候选版本，直到 Urgent 且难以复现的问题被确认修复
* 如果回归 Bug 在 2 天缺陷修复窗口内无法修复，将从发布分支中回退导致问题的提交（commit），并构建不包含这些更改的新发布候选版本

### Won't work 的强制规则

> **任何进入 `Won't work` 的 Issue，必须满足以下条件：**

* **重要说明**：Won't work 不等于问题不重要，而是当前资源和时机下的显性决策

* Issue 评论中必须写明：

  * 不做的原因
  * 决策背景
  * 当前资源和时机的限制
* 不允许只改状态、不写说明

目的：

* 防止重复创建 Issue
* 给 QA / PM / 新成员明确结论
* 记录决策依据，便于未来重新评估

## 标签（Labels）使用规则

### 4.1 标签是分类，不是流程

* 标签用于回答：

  * 这是什么类型的工作？
  * 影响哪个模块？
* 不允许用标签表达状态

---

### 4.2 必须使用的核心标签

**类型 (选一个)：**

* `Feature`
* `Bug`
* `Data`
* `Improvement`

**平台（Platform，选 1 个）：**

* `iOS`
* `Android`
* `iOS + Android`
* `Web`

## 各角色在 Linear 中的使用方式

### 开发Leader （Lead Developer）

* 使用 **Projects** 跟踪阶段性目标和整体进度
* 使用 **Active Issues** 监控当前执行状态和工作负载
* 使用 **Planning** 进行 Cycle Planning，给组员分配任务
* 使用 **Backlog** 将 Project 拆分为多个 Issue
* 使用 **Blocked** 查看被外部条件阻塞的工作
* 使用 **Won't work** 检查被拒绝的 Issue 是否写明原因
* **项目更新**：每个周期结束后，在 Retro 会议之后，开发Leader应该提供项目更新（Project Update）

---

### 开发成员（Developer）
* 使用 **Active** 推进 Issue 的状态流转
* 使用 **Issue 详情页** 更新状态、补充说明、关联 PR

---

### 产品经理（PM）/ 设计师（Designer）

* 使用 **Backlog** 创建新需求和
* 使用 **Projects** 跟踪整体进度
* 使用 **Issue 详情页** 在description中澄清需求和决策

---

### 测试 / QA

* 使用 **Backlog** 从测试或发布验证中创建新的 Bug Issue
* 使用 **Won't work** 检查问题是否已被明确拒绝，避免重复创建
* 使用 **Issue 详情页** 补充复现步骤、测试结果和证据截图和视频
