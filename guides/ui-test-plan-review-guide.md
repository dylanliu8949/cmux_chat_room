# UI 测试计划审查指南

UI 测试计划是自动化测试的规格书。它的唯一目的是让 AI agent 能够**不靠猜测**地生成正确的测试代码。审查的目标是确保计划达到这一标准。

UI 测试计划的核心失败模式与实现计划不同。实现计划失败在架构上；UI 测试计划失败在**准确性**上——agent 调用不存在的 API、使用错误的 Accessibility ID、或写出"通过"但不验证任何实质内容的测试。

**审查的边界**：审查评估的是计划的可执行性——API 引用是否准确、ID 是否一致、覆盖是否完整。审查**不评估**关联主计划中的设计选择。

> **参考资料**：编写稳定 UI 测试的原则、框架 API 和常见陷阱见 [`ui-test/docs/how_to_write_stable_ui_test.md`](../ui-test/docs/how_to_write_stable_ui_test.md)。

## 四种状态

| 状态 | 含义 | 后续动作 |
|------|------|----------|
| **未就绪 (Not Ready)** | 计划未满足审查的前提条件 | 开发者继续完善计划（补齐必需 section、添加关联主计划），然后重新提交审查 |
| **废弃 (Abandon)** | 计划已审查，存在根本性问题，无法通过局部修复挽救 | 废弃当前计划，从头重新生成 |
| **需要完善 (Needs Refinement)** | 计划已审查，方向正确，但存在 API 不匹配、覆盖缺口或验证质量问题 | 向开发者提出选择题，开发者决策后更新计划 |
| **可执行 (Ready)** | 计划已审查，API 准确、ID 一致、覆盖完整、验证充分 | 可直接执行 |

**未就绪**与其他三种状态的区别：未就绪是进入审查的前提条件检查，不是审查结果。计划不符合模板结构、或缺少关联主计划时，审查流程不会启动。

## 执行顺序：UI 测试计划在功能实现之后执行

UI 测试计划不是独立存在的——它假设**关联主计划已经被实现**。max_full_send 的流程是：

```
功能计划审查 → 功能代码生成 → UI 测试计划审查 → UI 测试代码生成
```

因此，审查 UI 测试计划时，必须区分两类引用：

| 类别 | 示例 | 审查方式 |
|------|------|----------|
| **App 侧代码**（关联主计划将创建） | AccessibilityIds 常量、UI 组件（按钮/菜单项）、ViewModel 方法、Service API | **不要**去代码库里验证它们是否存在。以关联主计划的描述为准。 |
| **测试 framework 代码**（Python） | `context_menu.py` 中的函数、`cache.py`、`__init__.py` 导出 | 验证方式：(a) 已存在于代码库中，或 (b) UI 测试计划在"需要修改/添加的文件"中描述了如何新增 |

**常见误判**：在代码库中 grep AccessibilityId 或 UI 按钮，发现"不存在"就判 FAIL——这些是关联主计划要实现的内容，还不存在是正常的。

## 护栏

1. **验证 Python framework API 时先读代码** — 计划说"函数 A 接受参数 X"，必须 Read 对应的 framework 源文件确认。但如果计划的"需要修改/添加的文件"中说明了要新增该函数，则视为合规
2. **不要验证 App 侧代码是否已存在** — AccessibilityIds、UI 组件、Kotlin/Swift 代码由关联主计划实现，以主计划描述为准
3. **不要猜测** — 如果无法确认某个 Python 函数是否存在或参数类型是否正确，Read 源文件确认
4. **不要自行修复计划** — 发现问题后向开发者提出选择题，由开发者决策后再更新计划

## 什么会导致「需要完善」

### 1. Framework API 不匹配

UI 测试计划的准确性核心。agent 在执行时会直接调用计划中描述的函数——如果函数不存在或签名不对，生成的代码无法运行。

常见问题：
- 参考资料中列出的函数签名与 framework 源文件中的实际签名不一致（参数名、参数类型、返回类型）
- 需要修改/添加的文件中描述的新函数，调用了不存在的底层 API
- 测试步骤中使用了 framework 中不存在的方法名

### 2. Accessibility ID 不一致

UI 测试通过 Accessibility ID 定位元素。以下引用必须完全一致：
- **关联主计划** 中 AccessibilityIds 部分定义的 ID（权威来源）
- **功能概述** 中列出的 ID（如 `layers_category_button`）
- **测试步骤** 中引用的 ID
- **需要修改/添加的文件** 中使用的 ID

任何一处不一致都会导致测试在运行时找不到元素。审查时应以关联主计划的 AccessibilityIds 定义为准。

### 3. 测试覆盖缺口

- 功能概述中列出的某个 UI 变更（按钮、菜单项等）没有对应的测试步骤
- 可见性条件只有正面断言（"X 可见"），缺少负面断言（"Y 不可见"）
- 涉及多个状态的功能（如菜单层级切换），只测试了部分状态转换
- 新增的交互元素（按钮、菜单项、对话框选项等）只验证了可见性，缺少点击后的行为验证。每个可点击元素都必须有对应的点击测试步骤并验证其效果（如：对话框有两个按钮，则两个按钮都需要测试点击后的预期结果）
- 测试步骤之间存在隐式状态依赖但未显式说明。如果 Step N 依赖 Step M 创建的元素或状态（如 Step 5 操作的是 Step 4 中 group 后的结果），计划必须明确这种前后依赖关系，否则 agent 可能在 Step N 中操作错误的元素

### 4. 验证质量不足

- 测试步骤的验证仅依赖 Appium 元素可见性检查（"按钮可见"），对于**状态变更**应使用 `debug_client` 断言（如 zIndex、lockedElementIds）
- 涉及变换操作（移动、旋转、缩放）的测试，未记录变换前的值进行前后对比
- Undo/Redo 测试未说明每步操作后的预期状态

### 5. 歧义

- 测试步骤中使用模糊描述（"选中一个元素"）而非具体的 framework API 调用（`gesture.select_all()` → 获取第一个元素 → 点击）
- 前置条件不明确（未说明如何进入编辑器、添加几个什么类型的元素）
- 涉及元素重叠/遮挡的场景，未注明处理策略
- 画布上存在多个同类型元素时（如 2 个文本元素），"选中第一个元素"是歧义的——必须说明如何区分目标元素（如通过 `debug_client.get_canvas_state()` 获取元素列表后按 index 或 id 选择）

### 6. 遗漏

- 某个 framework 模块在测试步骤中被使用，但参考资料中未列出
- 需要修改的文件未列出 `__init__.py` 的导出变更
- 测试文件的修改说明仅写"按上方步骤编写测试"，未按 Step 拆分
- `ui-test/e2e-tests/` 下的现有 e2e 测试会受到 UI 变更影响（如按钮移入子菜单、framework 函数行为变化、Accessibility ID 变更等），但计划未包含对这些测试的更新。e2e 测试运行在 CI 上，必须保持通过。（注意：`ui-test/feature-tests/` 下的测试不在此要求范围内）

## 什么会导致「废弃」

废弃意味着计划的基础有问题，无法通过局部修补挽救。以下任一条件成立即判定为废弃：

### 1. 与关联主计划矛盾

测试计划测试的功能与关联主计划定义的功能不一致。例如：主计划定义了三级菜单结构，但测试计划测试的是两级菜单。

### 2. 混入实现工作

测试计划应仅包含测试代码的变更。如果计划中包含修改 app 源码（Kotlin/Swift）的步骤，说明测试计划和实现计划的边界混淆，应当废弃。

### 3. 依赖不存在的测试 framework 能力

测试计划依赖 Python 测试 framework 中不存在且不在修改列表中的功能。例如：计划假设 `gesture.multi_select()` 存在，但实际 framework 没有这个方法且计划未将其列入需要新增的 API。

**注意**：这仅指 `ui-test/framework/` 下的 Python 代码。App 侧的 Kotlin/Swift 代码（AccessibilityIds、UI 组件等）由关联主计划实现，不属于此项检查范围。

## 「需要完善」时的输出规范

对每个发现的问题，向开发者呈现：

1. **问题是什么** — 在计划的哪个位置、具体是什么问题
2. **影响是什么** — 如果不解决，agent 执行时会发生什么
3. **选项** — 提供具体的修复选项供开发者选择

开发者做出选择后：
1. 更新计划中所有受影响的部分（参考资料、测试步骤、需要修改的文件等），确保全文一致
2. 重新检查一致性，确认更新后无新矛盾
