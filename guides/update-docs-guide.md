# 文档更新指南

本指南用于更新或新建模块文档（重点是 `docs/architecture.md`）。

## 文档类型

- `architecture.md`：模块架构说明。每个模块应有一份；新模块应基于 `templates/architecture-template.md` 创建。
- `how_to.md`：内部工具/流程使用说明，面向开发者与 agent。
- `guide.md`：针对某类任务的指导原则（可包含原则、规则、示例）。
- `index`：索引文档，帮助快速定位资料（如 `guides/encyclopedia.md`、`guides/dictionary.md`）。
- `other`：不属于上述类型的随机文档。

## update_docs.py 范围

`ralph/skills/update_docs.py` 只允许更新以下类型：
- `docs/architecture.md`
- `docs/how_to.md`
- `guides/encyclopedia.md`
- `guides/dictionary.md`

不允许更新 `guide.md` 和 `other` 类型文档。

## 写作原则

- **统一文风**：所有文档类型都写成说明文（描述事实、决策、约束、适用条件），不写劝说性论述。
- **事实与意图分离**：代码描述“当前是什么”；计划文档/已归档决策描述“为什么这样做”。
- **以可验证信息为准**：结构性章节基于当前代码；设计说明基于明确存在的计划或决策记录。
- **默认简洁**：优先短句、短段落、可扫描的条目；避免大段背景论述。
- **面向检索**：标题和术语稳定，便于 agent 与开发者快速定位。
- **图示规范**：模块依赖图与流程图统一使用 Mermaid 表达。
- **接口表格规范**：公开 API 统一使用表格汇总。列顺序固定为 `API`、`类型`、`主要能力`、`主要调用方`。每个公开类独占一行；其公开函数（先于变量）和公开变量/属性紧随其后，`API` 列用 `└ ` 前缀表示从属关系。不将多个类捆绑在同一行。
- **保持边界**：文档任务只改文档，不顺手改生产代码、测试或配置。
- **对齐知识索引**：新增重要文档时，同步评估是否需要更新 `guides/encyclopedia.md`。

## 新模块文档

- 新建模块时，`docs/architecture.md` 应基于模板 `templates/architecture-template.md` 创建。
- 模板提供结构骨架；内容应按模块实际情况填写（职责、依赖、公开 API、测试布局）。
- 创建新文档时，可参考现有模块的 `docs/architecture.md` 或 `docs/how_to.md`，优先复用已验证的写法与结构。

## 各节更新策略

每个 `architecture.md` 节更新遵循以下规则。**结构性节**以实际代码为准；**设计说明**以计划文档为准。

### 模块职责

以代码为准：读取模块顶层代码理解现有职责边界，更新时保留已有的设计意图描述，仅修正与当前代码不符的内容。不从代码推断"为什么这样设计"——这属于设计说明。

### 依赖关系

以代码为准：检查实际 import 关系、build 文件中的模块依赖、`__init__.py` 或公开 API 的导入路径，更新 mermaid 图和依赖列表。仅列真实存在的依赖，不列计划中尚未落地的依赖。

### 包结构

以代码为准：对比当前目录树与文档中的包结构，新增文件/目录需要反映在树形图中，已删除的需要移除。文件旁的注释只写一句话说明该文件做什么，不写为什么。

**格式**：包结构使用代码块内的 ASCII 树形图表达（`tree` 风格），根节点从模块源目录开始，每个文件行尾用 `# 一句话说明` 注释。示例结构见 [`canvas-editor/editor-service/docs/architecture.md`](../canvas-editor/editor-service/docs/architecture.md)：

```
canvas-editor/editor-service/src/
├── commonMain/kotlin/com/vibe/canvaseditor/
│   ├── di/
│   │   └── EditorServiceModule.kt          # Koin DI 模块
│   └── services/
│       ├── editorService/
│       │   ├── EditorService.kt             # 核心类
│       │   └── EditorService.Elements.kt    # 元素 CRUD
│       └── SessionManager.kt               # 会话管理
```

**创建**：新模块首次写包结构时，用 `Glob` 列出目录树，按实际结构手动排版为树形图，只列 `src/` 下的源文件，忽略构建产物和自动生成文件。

**更新**：每次有文件新增或删除时，对比目录树与文档，同步修改对应行。不重组树的层级结构，不修改已有文件行的注释（除非文件职责本身发生变化）。

### 可见性（公开 API / 内部组件）

以代码为准：扫描实际跨模块引用（用 Grep 确认），更新公开 API 列表。新增 API 条目时，从代码中复制定义和使用示例，不要自行构造示例。已删除的 API 从文档中移除。`internal` 组件列表同步更新。

### 单元测试

以代码为准：扫描测试目录，更新测试文件和覆盖范围表。测试描述从测试函数名/测试注释中提取，不自行解释测试意图。

### 设计说明

仅适用于 `architecture.md` 的 `## 设计说明` 章节：以计划文档为准，从 plan doc 提取本次变更引入的架构决策和设计理由，添加为新的决策条目（带 plan doc 链接）。不从代码观察推断设计动机；不修改已有决策条目的内容。

## 禁止的操作

| 类别 | 说明 | 为什么禁止 |
|------|------|------------|
| **修改非文档文件** | 编辑 `.py`、`.kt`、`.swift` 等源文件 | 当前任务范围仅限文档更新 |
| **重组文档结构** | 重命名章节标题、调整章节顺序、合并/拆分章节 | 破坏文档索引和已有引用 |
| **推断设计决策** | 从代码行为反推"为什么这样设计"并写入设计说明 | 会引入无依据的设计主张 |
| **更新无关文档** | 更新与本次变更文件不相关的 architecture.md | 超出当前变更范围，引入无端修改 |
| **伪造当前状态** | 把计划中尚未实现的内容写成已落地现状 | 让文档变得不可信 |
| **添加行号引用** | 在文档中使用"见第 N 行"或文件行号 | 行号频繁变化，引用会迅速失效 |
